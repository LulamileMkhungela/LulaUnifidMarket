# Architecture

One zero-dependency Node 22 process serves the REST API, the PWA and the
server-rendered pro microsites from a single origin. No build step, no
framework, no `node_modules` — the reference implementation is meant to be read
end to end and deployed anywhere a Node process runs.

## Layering rules

1. **HTTP never touches the store.** Routes call the `Marketplace` facade; the
   facade calls service modules; service modules call the kernel. That is the
   whole dependency graph, and it is what makes the 199 tests possible without a
   server. The one deliberate exception is `businessSites.js`, which renders
   HTML: it is a service that returns strings, still with no network and no
   template engine, and the HTTP layer only decides which URL serves which
   string.
2. **The kernel never calls out.** No network, no fs. Verification, escrow,
   risk and policy are pure state transitions over the ledger, so they are
   testable in milliseconds and portable to any runtime.
3. **Integrations never lie.** Every adapter returns `live` and, when false, a
   `reason`. Paid adapters in simulation return `WARN`/`UNAVAILABLE`, never
   `PASS`.
4. **Verticals are data, not forks.** A vertical is `{verificationProfile,
   criticalFields, lockedFields, requiredEvidence, defaultEscrowProvider,
   status}`. Adding a vertical does not touch the kernel.

## The state machines that matter

### Booking / escrow

```
AWARDED → AWAITING_PAYMENT → SCHEDULED → EN_ROUTE → ON_SITE → IN_PROGRESS
        → AWAITING_CONFIRMATION → IN_WARRANTY → CLOSED
exceptions: CANCELLED · REFUNDED · DISPUTED
```

Escrow underneath: `AWAITING_PAYMENT → FUNDED → (FROZEN ⇄) READY_FOR_RELEASE →
PARTIALLY_RELEASED → RELEASED`, with `REFUNDED`/`PARTIALLY_REFUNDED` branches.
The 5% holdback lives inside `PARTIALLY_RELEASED` until the warranty closes.

### Verification

```
PENDING → IN_PROGRESS → VERIFIED → ELITE
              ↓             ↓
        RECHECK_REQUIRED  (expired evidence / edits)
              ↓
           FAILED → REMOVED_FOR_RISK
```

A pro is *cleared to bid* only when the badge is one of
`IDENTITY_VERIFIED | PROVERI_VERIFIED | TRADE_VERIFIED | PROVERI_ELITE` **and**
the risk tier is below HIGH. Both facts are recomputed together by
`people.refreshStanding()` — badge and clearance can never drift apart.

### Business site

```
DRAFT → PREVIEW → LIVE ⇄ PAUSED → ARCHIVED
          ↓
       BLOCKED   (policy WEB-002: an asset has no permission record)
```

`BLOCKED` is not a status a human sets — `publish()` writes it when the
permission gate is closed and throws with the fired rules attached, so the
reason and the remedy travel together. Subscription underneath:
`TRIAL → ACTIVE → (PAST_DUE) → CANCELLED | EXPIRED`, with month one held in the
same escrow engine as a job and released by publishing.

### Sales lead

```
NEW → RESEARCHED → DIAGNOSED → DEMO_BUILT → CONTACTED → MEETING_BOOKED
    → PREVIEW_SENT → NEGOTIATION → WON
exceptions: LOST (with a reason) · NURTURE (not now, not never)
```

Every stage carries a forecast weight, so `weightedPipelineCents` is a number
somebody can be held to. A POPIA objection moves a prospect to `LOST` with
`result: 'OPT_OUT'` and blocks all six outreach channels; on a `WON` account it
records the objection and leaves the stage alone, because they are still a
customer.

### Portfolio item

```
(nothing)  ──addItem()──▶  SELF_DECLARED  ──link a released booking──▶  EVIDENCE_LINKED
                                     │                                          │
                                     │                                   confirmByClient()
                                     │                                   or a 4★+ review
                                     ▼                                          ▼
                              (patch claims a tier)                     CLIENT_CONFIRMED
                                     │
                                     └──PRT-001 BLOCK──▶ 409 + VERIFICATION_CLAIM_WITHOUT_EVIDENCE

bookings.releasePayment() ──harvestFromBooking()──▶ EVIDENCE_LINKED / CLIENT_CONFIRMED  (idempotent)

LIVE ──flag()──▶ FLAGGED (off the shelf, on the record) ──removeItem()──▶ REMOVED (soft)
```

There is no arrow from `SELF_DECLARED` to a tier that does not pass through a
released booking belonging to that pro, and no arrow out of `FLAGGED`/`REMOVED`
back to the feed.

## Concurrency and durability notes (honest)

The reference store is an in-memory `Map` graph with an optional JSON snapshot
(`PROVERI_PERSIST=1`). Production would swap `store.js` for Postgres/Neon behind
the same interface; the ledger would become an append-only table with the same
hash chain. Nothing above the store layer changes. The scheduler is a
`setInterval` sweep; production would run it as a queue consumer.

## Security posture

- No client secrets; partner keys are env-only and optional.
- Raw SA IDs and bank numbers are **never stored or echoed** — only SHA-256
  seals and masked forms cross an API boundary.
- Static serving blocks traversal and dotfiles; service worker is `no-cache`.
- Errors return a correlation id; stack traces never reach a client.
- `Permissions-Policy` limits geolocation/camera to the origin (the PWA asks
  only when capturing proof of work).
